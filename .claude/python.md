# Python Rules

## Runtime and tooling

- Target Python 3.12 unless the repository config says otherwise.
- Use `uv` for dependency management and command execution.
- Prefer `pyproject.toml` as the source of project configuration.
- Do not manually edit `uv.lock` unless required by the package manager workflow.
- Use `ruff` for linting and formatting policy.
- Use `mypy` or `pyright` when configured.

## Typing

- Prefer explicit type annotations on public functions, methods, dataclass fields, and Pydantic models.
- Avoid `Any` unless justified at a boundary.
- Prefer `Protocol` for behavior contracts.
- Prefer Pydantic models, `TypedDict`, or dataclasses over unstructured dictionaries.
  - Choose Pydantic models over dataclasses.
- Use `Self` where appropriate.
- Use `Literal` and `Enum` for constrained values.
- Keep generic types readable.

## Enums

- Use `enum.StrEnum` for string enums; do not use the `str, Enum` mixin.
- Use `enum.auto()` for member values; in `StrEnum` it yields the lowercase member name.
- Assign explicit values only when the required value differs from the lowercase member name, such as an external contract or persisted value.
- Name members in `UPPER_SNAKE_CASE`.

## Pydantic

- Use Pydantic v2 patterns.
- Use `BaseModel` for external data validation and structured LLM outputs.
- Use `pydantic-settings` for configuration.
- Prefer `model_config = ConfigDict(...)` over legacy config style.
- Prefer validators only when field types and constraints are insufficient.
- Prefer reusable `Annotated` types for field-level validation and serialization (`AfterValidator`, `BeforeValidator`, `PlainSerializer`, constraints via `Annotated[..., Field(...)]`) over `@field_validator`/`@field_serializer` decorators.
- Define shared annotated scalar types once and reuse them across models; the architecture layout reserves `types/scalars.py` for this.
- Use decorators only for model-specific logic or cross-field validation (`@model_validator`).
- Keep schemas close to the boundary they represent.

## Async

- Preserve async boundaries.
- Do not call blocking I/O inside async functions unless wrapped appropriately.
- Prefer async clients when the surrounding service is async.
- Avoid `asyncio.run()` inside libraries.
- Avoid fire-and-forget tasks unless lifecycle and cancellation are explicit.

## Error handling

- Raise specific exceptions.
- Do not swallow exceptions silently.
- Preserve exception context with `raise ... from exc`.
- Convert external exceptions into domain-specific errors at integration boundaries.
- Include actionable error messages.
- Avoid exposing secrets in exception messages.

## Functions and classes

- Prefer small, cohesive functions.
- Avoid large god classes.
- Avoid boolean parameters that create multiple hidden modes; prefer enums or separate functions when behavior diverges.
- Keep side effects explicit.
- Do not mix parsing, validation, I/O, and domain decisions in one function.

## Imports

- Keep imports explicit.
- Avoid wildcard imports.
- Avoid import-time network calls, file writes, database connections, or environment-dependent behavior.
- Use local imports only to break cycles or avoid optional dependency loading.

## Docstrings

Use numpydoc-style docstrings for public modules, classes, and functions when the behavior is not obvious.

### Human-friendly docstrings

Human-friendly means:

- explaining intent, not just syntax
- preferring plain language over jargon when possible
- saying what matters to the caller
- not sounding autogenerated
- not just restating the function name in sentence form

### Argument types

- Write parameter types in NumPyDoc form: `name : type`.
- For `**kwargs`, keep the leading asterisks and omit the type declaration, for example `**kwargs`.
- Document non-`None` defaults in the type line with `default=value`, for example `encoding : str, default="utf-8"`.
- Use `type, optional` for parameters that can be omitted because their default is `None`, for example `b : str, optional` for `b: str | None = None`.
- Use `type or None` for required parameters that accept `None`, for example `b : str or None` for `b: str | None`.
- Prefer readable container forms: `list of str`, `tuple of str`, `dict of str to int`, `Mapping of str to Any`.
- For fixed-shape tuples, use `tuple of (str, int)` when the element positions matter.
- For unions, use `str or Path`, `list of str or None`, or the narrowest readable equivalent.
- For callables and complex objects, name the concept clearly: `Callable`, `Callable[[str], bool]`, `type of BaseModel`, or the project protocol/model type.
- Match the signature exactly; do not document exceptions, defaults, or `None` unless the code supports them.
- Keep docstring types reader-facing: simplify Python syntax when it improves clarity, but preserve meaning. For example, prefer `list of str` over `list[str]`, `str or Path` over `str | Path`, and `Callable[[str], bool]` only when the callable signature matters.

Example:

```python
def normalize_location(raw_name: str) -> str:
    """Normalize a raw location name.

    Parameters
    ----------
    raw_name : str
        User-provided location name.

    Returns
    -------
    str
        Canonicalized location name suitable for matching.
    """
```

## Comments

- Prefer clear code over comments.
- Use comments for non-obvious business rules, invariants, trade-offs, or external system quirks.
- Do not add comments that simply repeat the code.

## Dependencies

Do not add a new runtime dependency unless:

- The standard library or existing dependency is insufficient.
- The dependency is actively maintained.
- The dependency has a compatible license.
- The dependency meaningfully reduces complexity.
- The user approves or the task explicitly requires it.

Prefer small, well-understood dependencies over large frameworks for narrow tasks.
